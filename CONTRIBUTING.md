## Code of Conduct

Be respectful and constructive in all interactions. Harassment, discrimination, and toxic behavior will not be tolerated.

## Development Setup

### Prerequisites

- **Java 21** or higher (required for Minecraft 1.21.1)
- **Git**
- **IDE**: IntelliJ IDEA (recommended) or Eclipse with Kotlin support
- **Minecraft 1.21.1** with **NeoForge 21.1.219+**
- **KotlinForForge** (NeoForge version)

### Getting Started

1. Fork the repository on GitHub
2. Clone your fork locally:
   ```bash
   git clone https://github.com/YOUR_USERNAME/create-station-voices.git
   cd create-station-voices
   ```
3. Open the project in your IDE:
   - **IntelliJ IDEA**: Open the `build.gradle` file and import as a Gradle project
   - **Eclipse**: Use the Gradle task `gradlew eclipse` then import the project
4. Run the Gradle setup tasks:
   ```bash
   ./gradlew genSources
   ```

### IDE Configuration

- Ensure your IDE is configured to use Java 21
- Enable Kotlin plugin (IntelliJ IDEA includes this by default)
- The project uses Kotlin 2.0.0 with JVM target 21

## Building the Project

### Build the Mod

```bash
./gradlew build
```

The compiled JAR will be in `build/libs/`.

### Run in Development

```bash
# Run client
./gradlew runClient

# Run server
./gradlew runServer

# Run game test server
./gradlew runGameTestServer
```

### Generate Data

```bash
./gradlew runData
```

## Running Tests

The project uses JUnit 5 for testing.

```bash
# Run all tests
./gradlew test

# Run a specific test class
./gradlew test --tests "TrainAnnouncerTest"
```

Test results are available in `build/reports/tests/test/index.html`.

## Code Style

### Kotlin

- Follow [Kotlin coding conventions](https://kotlinlang.org/docs/coding-conventions.html)
- Use 4-space indentation
- Maximum line length: 120 characters
- Prefer expression bodies for simple functions
- Use meaningful variable and function names

### Java

- Follow standard Java naming conventions
- Use 4-space indentation

### General Guidelines

- Write clear, self-documenting code
- Add comments for complex logic
- Keep methods focused and concise
- Write unit tests for new functionality
- Update documentation when changing behavior


## AI-Assisted Contributions

### AI Assistance is Welcome

We welcome contributions that use AI tools (such as GitHub Copilot, ChatGPT, Claude, etc.) as part of the development process. **AI-Assisted** commits are perfectly acceptable when:

- You have reviewed and understood the AI-generated code
- You can explain and justify the changes during code review
- The code follows our style guidelines and best practices
- You take full responsibility for the quality of the contribution

### No "Vibe-Coded" Contributions

We do **not** accept contributions that appear to be entirely "vibe-coded" (i.e., code that seems to have been generated by AI without any human review or understanding). Signs of vibe-coded contributions include:

- Code that doesn't match the project's style or patterns
- Nonsensical or hallucinated API usage
- Irrelevant or redundant code
- Lack of understanding when asked about the implementation
- Changes that clearly haven't been tested

### Best Practices for AI-Assisted Work

If you use AI tools:

1. **Review thoroughly**: Read every line of AI-generated code before committing
2. **Test locally**: Ensure the code compiles and runs correctly
3. **Understand the logic**: Be prepared to explain your changes
4. **Refine as needed**: Edit AI suggestions to match project conventions
5. **Respect Licensing**: Ensure the AI hasn't blatantly copied recognizable proprietary code from other projects
6. **Mark as AI-assisted** (optional): Consider noting "AI-assisted" in your PR description for transparency

Remember: AI is a tool to enhance your productivity, not replace your judgment. All contributions should reflect that a human has carefully reviewed and validated the changes.

## Submitting Changes

### Pull Request Process

1. Create a feature branch from `main`:

   ```bash
   git checkout -b feature/your-feature-name
   ```
2. Make your changes, following the code style guidelines
3. Add or update tests as needed
4. Ensure all tests pass:

   ```bash
   ./gradlew test
   ```
5. Build the project successfully:

   ```bash
   ./gradlew build
   ```
6. Commit your changes with clear commit messages:

   ```bash
   git commit -m "Add feature: brief description"
   ```
7. Push to your fork:

   ```bash
   git push origin feature/your-feature-name
   ```
8. Open a Pull Request on GitHub

### Pull Request Guidelines

- Provide a clear description of the changes
- Reference any related issues (e.g., "Fixes #123")
- Keep PRs focused - one feature or fix per PR
- Ensure CI passes (tests, build)
- Be responsive to code review feedback

### Branch Naming

- `feature/` - New features
- `fix/` - Bug fixes
- `refactor/` - Code refactoring
- `docs/` - Documentation changes
- `test/` - Test additions or modifications

## Reporting Issues

### Before Reporting

1. Check if the issue already exists in the [issue tracker](https://github.com/JaMaLa1111/create-station-voices/issues)
2. Try the latest version to see if the issue persists
3. Gather relevant information:
   - Minecraft version
   - NeoForge version
   - Create mod version
   - Other installed mods (if relevant)
   - Crash reports or logs (from `logs/latest.log`)

### Issue Template

```
**Description**
A clear description of the issue.

**Steps to Reproduce**
1. Step one
2. Step two
3. ...

**Expected Behavior**
What you expected to happen.

**Actual Behavior**
What actually happened.

**Environment**
- Minecraft: [version]
- NeoForge: [version]
- Create: [version]
- Create: Station Voices: [version]

**Logs/Crash Reports**
Paste relevant logs or attach crash report files.

**Screenshots**
If applicable, add screenshots.
```
